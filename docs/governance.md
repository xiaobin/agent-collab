# 团队治理与版本

## 单一正本

`agent-collab` 是你和团队公共协作流程的唯一正本。团队成员通过内部 marketplace 安装发布版本，不在各项目复制、改写公共 Skill。项目可增加更严格的规则，但不能自行削弱公共安全、权限和验收要求。

## 变更审批

以下属于公共核心契约，变化需要用户确认：

- 目标和范围确认要求；
- 人与 agent 的决策边界；
- 安全、权限、提交、推送、发布和共享环境门禁；
- 完成定义、覆盖度、独立复审和业务验收要求；
- 评估门禁、归因口径，以及画像被用于派单、淘汰或自我改进的边界；
- 允许排除或降级功能的条件。

以下属于技术维护，可在不改变上述语义的前提下自主完成：

- 文字澄清、错别字、目录和代码组织；
- 不改变行为契约的参考文件拆分；
- 补充测试、 fixtures、结构校验和文档示例；
- 修复脚本错误，同时保持或加强原有检查。

任何修改都不能用“技术维护”名义暗中放宽核心契约。

## 版本策略

使用 SemVer：

- MAJOR：任务卡结构或公共行为出现不兼容变化；
- MINOR：向后兼容的新流程、模板或校验能力；
- PATCH：澄清、错误修复和测试增强。

`plugin.json` 与 marketplace entry 的版本必须一致。每次发布更新 `CHANGELOG.md`，说明行为变化、迁移动作和是否影响任务卡。

## 发布检查

1. 工作树只包含本次发布范围。
2. `./scripts/verify.sh` 全部通过。
3. 检查公共契约变化是否已有用户确认。
4. 检查文档、模板、脚本引用和版本一致。
5. 更新 CHANGELOG，并评估现有项目升级是否需要迁移。
6. 仅在获得提交、推送或发布授权后创建相应 commit、推送和 release tag。

初期由成员审查后主动更新，不自动追新版本，也不启用 managed settings 强制安装。

## 改进纪律

优先修改能解决问题的最便宜载体：Skill、脚本、复审流程，最后才增加常驻提示。修改应有失败行为、测试或对比证据；不为了“看起来更完整”增加规则。

一次修改多个组件且没有隔离验证时，不声称某一条规则独立产生效果。没有证据支持的修改可以保留基线，不把“变更数量”当改进成果。

## 基于评估的自我改进

评估记录是改进输入，不是自动决策器。流程改进走版本化提案：

```text
提案 → 独立复审 → 小范围试用 → 对比评估 → 保留或回滚
```

- 提案必须写清改动的 Skill、脚本或 hook，预期效果和失败信号。
- 独立复审检查是否放宽安全、权限、验收或数据边界。
- 对比使用同一快照和同一验收口径；样本不足时不宣称改善。
- 不自动淘汰 agent、不自动部署、不上传或发布个人与项目数据。
- 核心契约、安全、发布和数据迁移决策仍由人确认，不由评估分数触发。
