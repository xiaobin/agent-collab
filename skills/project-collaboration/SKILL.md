# 项目协作

把沟通落实为可恢复的目标、边界、行动和证据，不以“已说过”“测试通过”或 agent 自述代替完成。

本文 `<skill_dir>` 指本 Skill 所在目录：Claude Code 中为 `${CLAUDE_PLUGIN_ROOT}/skills/project-collaboration`；Pi 和 Codex 使用各自加载技能时显示的绝对路径。下列命令从项目根目录运行，任务卡和证据路径相对项目根目录解析。

## 1. 启动或恢复

1. 找目标权威来源：当前用户指令、PRD、Issue 或已确认任务卡。聊天记录和 memory 只作背景，不能覆盖更新的用户指令。
2. 读取项目 `AGENTS.md`；若存在 `.herdr/current-task.json` 和 `.herdr/PROGRESS.md`，先恢复原任务，不另起相互竞争的任务。
3. 涉及现有代码、配置、接口、数据或页面时，先调查受影响面。多仓场景先判断权威源，不只调查最方便的一份。
4. 非简单问答或单步操作，建立或更新 `.herdr/current-task.json`。以插件 `templates/current-task.json` 为结构，写清：
   - 目标及 `goal_ref`；
   - 范围、非目标、依赖和风险；
   - 可执行验收项、业务验收责任人；
   - 自主决策与必须交回用户的边界。
5. 开工前运行：

   ```bash
   sh "<skill_dir>/scripts/validate-task.sh" .herdr/current-task.json --phase dispatch
   ```

   简单任务可不建状态文件；复杂任务必须让范围可逐项核对。

用户已经给出完整目标和授权时，直接记录并推进，不重复询问“是否开始”。只有关键歧义会改变交付物、权限或验收时，才请求确认。

## 2. 对齐目标与边界

用简短任务卡复述，而不是长篇反问：

```text
目标 / 范围 / 非目标 / 验收 / 权限 / 当前未知项
```

区分两类事项：

| agent 可自主 | 必须交回用户 |
| --- | --- |
| 已确认边界内、可逆、无外部影响的实现选择 | 改变对外契约、交付范围或验收标准 |
| 文件落位、任务拆分、并行度、普通修复与补测试 | 放宽安全、权限、鉴权或沙箱边界 |
| 同一验收标准下的调查、复现与取证 | 部署、发布、生产或共享环境写操作 |
| 放弃失败路线、恢复错误修改 | 未获明确授权的提交、推送、销毁性操作 |
| 已冻结规范内的技术取舍 | 功能无法完整交付，或需要排除、降级目标功能 |

需要用户决策时，给一个推荐方案，说明理由、影响和授权范围；不罗列一堆技术选项。已确认事项不重复请示。

详见 [决策边界与记录](references/decisions.md)。

## 3. 执行与过程沟通

- 开工前：说明建议流程、交付物、同步节点和硬门禁。
- 阶段出口：按“完成什么 → 验证结果 → 风险 → 下一决策”同步，不报模糊百分比。
- 执行中：需要时使用“现状—障碍—下一步—需要支持”。
- 风险早报：区分已知事实、影响、未知项和建议。
- 对重要歧义进行复述校验：“我理解的是 X；如果实际是 Y，交付物会变为 Z。”
- 关键讨论以行动项闭环：结论、执行者、下一同步节点。

默认在初步调查后、复杂方案形成后、关键里程碑和最终交付沟通。目标或范围变化、重大风险、额外权限、真实阻塞、无法按原验收完整交付时立即沟通。已确认计划内的普通实现、可逆技术选择和常规补测试不额外打扰。

汇报先给人话结论，再按 `总目标 / 任务边界 / 需要改动的内容 / 本轮 / ✅ 已完成 / 🔜 接下来 / 🙋 需要你` 的结构展开：总目标写明目标来源和阶段骨架，任务边界写明范围内、写范围、非目标和授权边界，改动清单逐项列出位置、改动和状态。首次汇报、里程碑和交付必须列全；日常短同步可省略表格，但不得省略目标来源和当前写范围。证据与内部编号后置；没有需要用户处理的事就明确写“暂无，你无需操作”。

详见 [过程沟通](references/communication.md)。

## 4. 派单与并行

没有目标来源不派单。只有存在明确目标、写范围和验收命令时才派单。每个任务写清 `task_id`、`attempt_id`、`goal_ref`、绝对 `cwd`、允许修改范围、依赖、验收和超时。

- 无依赖且写范围完全不重叠才并行；同一路径同一时间一个 writer。
- worker 不直接指挥其他 worker；跨 lane 的派单、取消、重试只由协调者发起并写入 ledger，避免出现账本之外的隐式 Attempt。
- 共享契约、锁文件、配置、格式化和数据库 migration 单点串行。
- agent 必须进入目标仓库工作，不在未经指定的仓库外副本修改。
- 派发前查阅同类历史评估，记录选择理由、样本量和已知风险；样本不足标 `insufficient_data`，它表示没有可信排名，不是禁用。
- 派发前记录任务与授权；回收时检查真实 diff、亲自重跑验收，再由独立 reviewer 审查。
- `done` 只触发回收；`timeout` 或失联只触发对账，不盲目重发。

完整进入/出口条件见 [生命周期](references/lifecycle.md)；评估字段、门禁和派单画像见 [Agent 评估](references/evaluation.md)；使用 Herdr 时按需读取 [Herdr 编排适配](references/herdr.md)，不把 Herdr 变成所有项目的硬依赖。

## 5. 验证与交付

完成必须同时满足：

1. 范围基线逐项闭环；差集为空，或排除项已有用户明确确认。
2. 实现、异常路径和测试齐备，没有占位实现、跳过测试或空验收。
3. 协调者亲自重跑验收命令，记录真实退出码、测试数量和关键输出。
4. 重要改动经过独立只读复审；实现者不能自审替代。
5. 技术验证与业务验收分开。编译、单测或手动触发不能自动替代真实业务链路。
6. 所有未验证项、遗留风险、权限边界和回滚条件明确披露。
7. 每个 Attempt 都有评估记录；最终通过前 `agent_eval.py check --final` 返回 0。业务验收未执行时保持 `pending`，不得写成通过。

详见 [证据验收](references/acceptance.md) 与 [Agent 评估](references/evaluation.md)。

## 6. 暂停、恢复与收尾

更新 `.herdr/PROGRESS.md`，至少写清当前阶段、已验证覆盖、下一动作、需要用户事项、在飞任务、占用资源和恢复第一条命令。状态文件只记运行事实，不复制完整通用流程。

收尾时释放本次创建且不再需要的资源，保留失败证据和审查记录。只把可迁移且有证据的教训回流到项目文档或公共包；一次性事实不写成永久规则。

详见 [状态与交接](references/handoff.md)。

## 7. 自动化 Bot

项目明确要建立自动化 bot，且用户已给出 `goal_ref` 时，先按 [Bot 框架](references/bot-framework.md) 起草定义、校验、请求批准，再运行。运行时已支持 `process` 运行时、`fake` 与只读 `feishu` 适配器、`run --once` 与 `--resident` 常驻模式；不调用模型改写用户数据，常驻与分诊只在批准范围内执行。Bot 由 Agent 起草，用户批准，运行时启动；Bot 不能创建 Bot 或自行扩权。

用户要「接入飞书同步」「让待办每天自动拉下来」时，唯一入口是 [bot-onboarding](../bot-onboarding/SKILL.md)：Claude Code `/agent-collab:bot-onboarding`、Pi `/skill:bot-onboarding`、Codex `$agent-collab:bot-onboarding`。该 Skill 负责探测、生成配置、校验、请求批准、首次只读运行和报告；不要另起第二套命令让用户执行。
