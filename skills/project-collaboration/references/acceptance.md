# 证据验收

## 完成定义

完成不是“代码写了”或“测试全绿”，而是目标范围逐项完成实现、技术验证、独立复审和业务验收。每个完成声明都应能回答：依据哪个目标、覆盖哪些范围、证据在哪里。

## 覆盖度

交付前列出范围基线与实际结果的差集：

- 已验证项 / 总项；
- 未覆盖项及原因；
- 排除项对应的用户确认；
- 不适用项及可核对的理由。

不得因缺少中间件、环境、依赖或实现难度自行排除目标功能。测试可使用进程内替身隔离，但生产实现不能因此被删除或降级。

## 技术验证

协调者或验收者亲自执行验收命令，记录：

```text
命令：
工作目录：
退出码：
测试数量：
关键输出：
对应验收项：
```

退出码非零即未通过；测试数量为零不能算测试成功。除退出码外，还应检查真实副作用、生成物和接口结果。

## 反证与回归

关键修复尽量提供反证：撤掉修复或注入原缺陷时，对应测试应失败。每轮修复都重跑已通过项的固定回归集，避免新修复破坏旧功能。

## 独立复审

Reviewer 只读检查逻辑、安全、接口兼容、缺失测试和越界修改。Reviewer 看 diff、范围基线和测试原文，不接受实现者“已经完成”的结论。作者与最终批准应分离。

## 验收顺序与结论

按顺序确认，前一步不成立就不进入下一步：

1. **归属**：task、agent、pane、Attempt 与回执一致，agent 已稳定。
2. **Git**：修改在允许范围内，没有混入任务开始前的脏变更、依赖升级、全仓格式化或无关文件。
3. **测试**：验收者亲自重跑命令并记录退出码；agent 自述不能替代。
4. **复审**：重要改动有独立只读复审，reviewer 不接受实现者结论。
5. **覆盖**：范围基线与实际结果的差集为空，或有用户确认的豁免。
6. **业务验收**：真实链路和责任人确认；未执行就写“未验证”。

结论只用四种：

- `SUCCEEDED`：上述证据齐备，目标范围逐项闭环。
- `FAILED`：逻辑、测试、范围或复审明确不通过。
- `BLOCKED`：缺少外部条件、权限或用户决定，当前无法继续。
- `UNKNOWN`：证据不足、状态不确定或尚未完成核验。

缺少任何必需证据时只能记 `UNKNOWN` 或 `BLOCKED`，不能因为“看起来没问题”记 `SUCCEEDED`。`done` 只表示 agent 已稳定，不是业务结论。

## 修复轮次

同一缺陷的修复按可执行条目派发，而不是重复一句“已修复”：

- 每轮最多合并 3 个相关缺陷，按模块收敛；完成定义写成“测试名 + 命令 + 预期输出”。
- 每项修复尽量演示“撤掉修复则测试失败”，否则视为未证明。
- 回传要带测试方法名和测试统计原文，验收者用 `grep -c '@Test'` 或测试名比对核对，虚报直接判 `FAILED`。
- 每轮复审重跑已通过项的固定回归集；本轮发现的检查盲区补进项目的验证门禁。
- 同一缺陷两轮未过就升级：换方案、缩小范围或交回用户，不允许同法重试第三轮。

## 技术验证不等于业务验收

以下证据只能证明对应技术层，不自动证明业务完成：

- 编译或 lint 通过；
- 单元测试通过；
- 手动触发接口成功；
- agent 的完成自述；
- 截图或单一快乐路径。

业务验收要按真实用户链路、真实角色和约定数据验证，并由责任人确认。尚未执行的业务走查必须标为“未验证”，不能改写为通过。

## 交付说明

至少包含范围覆盖、已执行命令与结果、独立复审结论、业务验收状态、未验证项、遗留风险、回滚条件，以及是否需要用户后续操作。
